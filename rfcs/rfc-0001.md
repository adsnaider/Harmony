# Summary

Define the main IPC mechanism used in the OS

# Overview

We need a way to define the connections of the component graph in such a way
that is composable, modular, and easy to manage. Components interact with
one another through synchronous invocation calls and shared memory. The IPC
mechanism that we define here will be the lifeline of the OS and, as such,
this design will have broad consequences on the rest of the system.

# Goals

* Define the mechanics of IPC over synchronous invocations and shared memory.
* The IPC should have function call semantics.
* The mechanics of composition should be handled through configuration, not
code.
* IPC composition should be secure. In particular:
  * A server (resource provider) must have a way to restrict access to its
  resources, that is, it must be able to limit which clients have access.
  * A client must have the ability to verify the integrity and authenticity of
  a server.

# Design

This design has 2 important pieces to consider. First, a DSL used for
defining components and interfaces that is compiled to code (code-gen tool).

The other piece is the composer component that defines the low level interface
for setting up the sync calls and shared memory interface, through secure
procedures.

# Component definition language - CDL

The component definition language (CDL), is be akin to protobufs, flatbuffers,
FIDL, etc. in that it will allow defining structs and procedure declarations,
that a server must implement and a client can call into as if it was a local
function call. [FIDL][fidl] is a great example as it is specifically used in
Fuchsia for its IPC.

[fidl]: https://fuchsia.dev/fuchsia-src/concepts/fidl/overview

There are some clear needs for a language like this, and the following are some
of the requirements

* There is a way to define algebraic data types
* There must be a way to define interfaces
* The RPC and data on wire must be consistent and future-proof

From the perspective of servers:

* There is a way to define which interfaces are implemented by the server
* There is a way to control which clients get access to its interfaces in a
granular level

From the perspective of clients:

* There is a way to define which interfaces are needed for a client
* There is a way to verify trust on servers


## Component Graph Examples

The following are some examples of components and what their CDL might look
like. The purpose of this section is to demonstrate the viability of the DSL
on these examples

### Scheduler

```cdl
struct Tid {
  tid: usize,
}

interface sched {
  fn yield();
  fn tid() -> Tid;
}

struct Sem {
  id: usize,
}

interface semaphore {
  fn new() -> Sem;
  fn inc(sem: Sem);
  fn dec(sem: Sem);
  fn drop(sem: Sem);
}
```

### Memory Management

```cdl
struct Page {
  addr: usize,
}
struct Frame {
  addr: usize,
}

enum Result<T, E> {
  Ok(T),
  Err(E),
}
struct Oom;

enum MapError {
  ...
}
enum UnmapError {
  ...
}

interface memory {
  fn alloc(count: usize) -> Result<[Frame], Oom>;
  fn dealloc(frame: Frame);
  fn map(page: Page, frame: Frame) -> Result<(), MapError>;
  fn unmap(page: Page) -> Result<Frame, UnmapError>;
}
```

### Composer

While the composer is the component that is in charge for consuming these CDLs
and linking sync calls from one component to another, it's possible to use CDLs
in a meta way to define the Composer server as a CDL that has some bootstrap
magic to have it connect things properly

```cdl
struct Handle {
  cap_id: usize,
}

enum LinkError {...}

interface composer {
  fn link(interface: uuid) -> Result<Handle, LinkError>;
}
```

## Common Patterns

The following patterns appear repeatedly and there's value in the language
supporting it better

1. **Opaque types**: These aren't a requirement as they can be implemented akin
to file descriptors but it's annoying to do that repeatedly and the language
could support opaque types as a first class primitive although that may require
some form of memory management to be pre-implemented. 
1. **Capability passthrough**: There are situations in which we may want to
expose a capability by sending it from one component to another. This could be
handled with some more *composer* meta-magic. Since the composer is in charge
of capability management, it could intercept capability messages and
automatically add the capability to the cap table. The incoming message would
have the cap ID in the message set to the new capability that got copied.


## Composer 

This section aims to describe the composer component which will be in charge of
managing capabilities and memory. While the CDL and the composer will be
related to one another, the aim here is to define the composer in lower-level
terms

### System bootstrap

At boot-time, the initial booter component is in charge of system
initialization. Once that is complete, the booter will be repurposed as the
composer. In the future, the booter may be changed to a configurable component
that will be in charge of initializing many components. However, since the
booter won't be the final owner of system resources, it becomes especially
tricky to allocate the requred resources in a way that can be recycled later
in the boot cycle.
